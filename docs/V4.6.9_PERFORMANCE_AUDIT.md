# V4.6.9 Performance 性能审计（第一阶段）

审计基线：提交 `c901b90` 加当前工作区 V4.6.9 排版修复。远端 HEAD 与本地提交一致。审计日期 2026-09-14。

本阶段只增加 `benchmarks/`，未修改导入、量测、ROI 或渲染算法。所有耗时为本机实测中位数或单次昂贵案例实测；未完成的规模明确标注。原始数据见 `audit_outputs/performance_20260914/benchmark_results.csv`。

## 1. 结论

当前有四个彼此独立的性能问题：

1. 通用 XYZ/Pixel/quoted/tab/whitespace 导入由 Python 逐行分词、逐 token 校验和字符串表构建主导。2M CSV 读取 12.11 s，而 warm-cache 顺序读仅约 0.03 s，干净数值文件的 pandas C parser 候选为 0.366 s。磁盘和 DataFrame 本身不是主因。
2. Smart ROI 的规则矩阵拓扑被 Python 字典、边列表、每点一个 ndarray 的邻接表和 Python BFS 主导。5M 拓扑 40.34 s，surface-following 74.89 s。
3. Physical XYZ 的 cKDTree 不是主要瓶颈。1M adaptive topology 96.93 s，KDTree build/query 只占约 0.2/1.29 s；逐行扇区选边、去重、每点 percentile 和邻接转换占绝大多数。
4. 默认 30k LOD 避免了百万点 Matplotlib 灾难，但 LOD 自身按全量点扫描、分配和排序。8M LOD 4.43 s；完整 GUI 刷新 15.46 s。四个 30k 画布约 0.55 s，剩余主要是同步 LOD、1/2/3 阶拟合、数组索引和显示快照。

平面指标不是首要瓶颈：2M `compute_plane_metrics` 0.211 s，5M 0.315 s，8M 0.529 s。它不值得优先 GPU 化。

## 2. 环境与方法

- CPU：Intel Core i5-12400F，6 核 12 线程；内存 31.9 GiB。
- GPU：RTX 2060 6 GiB；本轮未安装或运行 CUDA/CuPy。
- Python 3.13.14；NumPy 2.5.2/OpenBLAS；pandas 3.0.5；SciPy 1.18.1；Matplotlib 3.11.1；Qt/PyQt 6.11。
- 100k、500k、1M、2M、5M；kernel 与 GUI 另测 8M。
- synthetic 规则扫描及轻微 XY jitter Physical 数据。文件生成不计时；文件读取是 OS warm-cache，因此报告不声称冷盘或网络盘速度。
- 数值 kernel 重复 3 次取中位数；昂贵导入和 Smart ROI 为单次独立进程实测。RSS 每 20 ms 采样。
- GUI 为 1600×900 Qt offscreen，保留真实窗口、事件循环、Matplotlib QtAgg 和 XY 后台任务；不能代表桌面合成器帧率。
- Physical Smart ROI 测到 1M 后停止：1M 已需约 113 s（拓扑+surface-following），2M/5M 会占用数分钟且不增加瓶颈判断。未用线性外推冒充实测。

## 3. 当前性能架构

```text
文件 -> 编码/格式/正文扫描 -> 各格式 parser -> 字符串或数值 DataFrame
     -> apply_mapping/to_numeric/单位转换 -> df_raw
     -> 变换缓存 -> ROI/滤波 -> 平面与 1/2/3 阶诊断拟合
     -> 30k spatial LOD -> 3D/XZ/YZ Matplotlib
     -> 全量 XY snapshot -> 后台 scan-grid/KDTree + raster -> imshow

Smart ROI:
matrix_rc -> Python matrix8 edges -> list[ndarray] adjacency -> Python grow/BFS
Physical  -> cKDTree -> Python adaptive edge selection/pruning -> 同一 adjacency/grow
```

导入和 Smart ROI 已放到 Qt worker；这改善响应性，但不会缩短 Python 热循环。常规 `update_analysis()` 和 LOD/三阶拟合仍在 GUI 线程。

## 5. 导入审计

### 路径与实测

| 格式，2M 点 | 当前解析 | 候选基准 | 主要原因 |
|---|---:|---:|---|
| Physical CSV | 12.115 s | pandas C 0.366 s | 每行 `csv.reader`、合法性检查、字符串 DataFrame |
| quoted CSV | 12.059 s | pandas C 0.370 s | 同上；C parser 保留 quoted CSV 语义的机会高 |
| tab XYZ | 12.069 s | pandas C 0.380 s | 当前仍走逐行 tokenizer |
| whitespace XYZ | 10.781 s | pandas C 0.932 s | 当前每行 regex split；C whitespace 候选较慢但仍显著更快 |
| Pixel XY | 11.985 s | 未直接替换 | parser 后还有像素完整性、拓扑行列和单位转换 |
| Zygo XYZ | 8.304 s | 未直接替换 | 专用正文边界、No Data、像素/物理坐标语义 |
| Z Matrix | 4.240 s | `fromstring` 单纯正文约 0.28 s（按 5M 比例之外不外推） | metadata+完整性预扫描+正文再次解析 |
| Keyence/VR synthetic matrix | 4.384 s | 与 Matrix 同类 | metadata 格式仍需真实文件校验 |

规模曲线：CSV 100k/500k/1M/2M/5M/8M = 0.595/2.716/5.683/12.115/29.504/48.367 s。Z Matrix = 0.250/1.115/2.113/4.240/9.479/13.361 s。Zygo = 0.353/1.798/3.846/8.304/20.222 s。

5M Matrix 细分：raw IO 0.022 s；metadata scan 3.544 s；完整性 prescan 2.814 s；`_read_height_matrix_table`（含 prescan、正文读取、建表）5.909 s；坐标/DataFrame 0.257 s；端到端 `_read_table` 9.479 s。嵌套阶段不可相加。

### 适用 parser 判断

- pandas C parser：适合已识别的单字符分隔、稳定列宽的普通/quoted CSV、TSV；必须限定 `usecols` 并做等价坏行/缺测测试。当前强制 `engine='python'` 没有必要覆盖全部格式。[pandas 文档确认 C/Python/PyArrow 三种引擎及 memory_map 支持](https://pandas.pydata.org/pandas-docs/stable/user_guide/io.html?highlight=s3fs)。
- `numpy.fromstring`：非常适合纯数值 Z Matrix 行或无引号 whitespace XYZ；不适合 quoted CSV、混合辅助文本列、`No Data` 多 token 记录。5M 干净矩阵候选 0.701 s，但它跳过了生产校验，不能直接把 13.5×写成可交付收益。
- PyArrow CSV：值得做可选候选 benchmark，尤其固定 schema 的 CSV/TSV；需显式列类型及 invalid-row handler，因为其类型推断首块后冻结。[Arrow 文档](https://arrow.apache.org/docs/python/csv.html)。本环境未安装，暂无真实性能数字。
- Polars：同样只能列为实验候选；需显式 schema 或扩大推断区间，[Polars 文档](https://docs.pola.rs/api/python/stable/reference/api/polars.read_csv.html)。它会扩大部署依赖，优先级低于内置 pandas C path。
- mmap：当前对“文件位置抽样”合适；对全量解析本身不会消除 tokenization/float 成本。warm IO 已远小于解析，单纯 memory-map 不会解决全量导入。
- chunk streaming：适合全量数值解析和受控峰值内存；应直接写入预分配/分块数值缓冲区，避免 `list[list[str]]`。抽样路径已经 bounded，但 Z Matrix 抽样仍要做完整性 prescan，因此 5M sampled 11.90 s，甚至慢于同次 5M full 9.48 s；它主要保护分析内存，不是导入加速。

## 8. 内存热点

理论最小值：float64 XYZ = `N×3×8`，5M 为 114.4 MiB，8M 为 183.1 MiB。bool mask 分别 4.8/7.6 MiB；int64 active index 38.1/61.0 MiB；一次 XYZ copy 再增加 114.4/183.1 MiB。

实际峰值显著更高：

| 场景 | 5M RSS 峰值/步骤增量 | 8M RSS 峰值/步骤增量 |
|---|---:|---:|
| CSV parser | 1691/1536 MiB | 2615/2460 MiB |
| Matrix parser | 806/651 MiB | 1259/1103 MiB |
| Matrix topology | 3452/3136 MiB | 未运行 |
| GUI refresh | 1711/1265 MiB | 2632/2023 MiB |
| LOD | 940/403 MiB | 1434/667 MiB |
| 三阶拟合 | 1380/839 MiB | 2115/1343 MiB |

不必要或可合并的复制点：

- `_apply_transform_pipeline` 即使 pipeline 为空也复制 X/Y/Z；8M 约 183 MiB 常驻缓存。缓存命中虽是 0 ms，但首次总会复制。
- `update_analysis` 先 `idx`，再 `xb/yb/zb`，再 `active_idx`，再 `fx/fy/fz`；无滤波时可避免部分高级索引副本。
- `draw_plots` 保存全量 `_smart_seed_view_indices['XY'] = xy_source_idx.copy()`，又将 `xy_x/y/z = tx[xy_source_idx]...` 作为 XY worker snapshot；Smart ROI worker再复制 finite index、XYZ、matrix row/col。
- `spatial_lod_indices` 生成 source、xx、yy、finite、ux、uy、ix、iy、cell、distance、nearest、候选和排序索引；这解释 8M 约 667 MiB 增量。
- 三阶拟合创建约 `N×10×8` 的设计矩阵：5M 单矩阵约 381 MiB，连同 normalized arrays、fitted/residual 达到约 839 MiB 步骤增量。
- CSV parser 的 `list[list[str]]` 和每个 token Python 字符串远超最终 3 列数值数据。
- Smart topology 的 `list[ndarray]` 加边列表、字典和临时 set 是最大内存风险。5M 步骤增量约 3.1 GiB。

`df[['X','Y','Z']].to_numpy()` 是否复制取决于 DataFrame block 是否合并；不能按 API 名一概判断。应在性能实现中用 `np.shares_memory`/峰值测试锁定每条真实路径。

## 9. Numba 适用性

| 类别 | 函数/模块 | 当前实现 | 预计价值 | 风险 |
|---|---|---|---|---|
| A 很适合 | matrix8 边/CSR 构建、health component、plane-residual component | Python dict/list/deque | 3–15× kernel；首次 matrix Smart ROI 2–5× | 必须保持缺点映射、8邻域和遍历语义 |
| A 很适合 | adaptive kNN 扇区选边、edge pruning/local scale | cKDTree 后 Python row loop/list percentile | 3–8×该部分；Physical topology 2–5× | tie/order、percentile 和边剪枝必须完全一致 |
| A 很适合 | surface-following grow | Python deque、标量邻点、周期局部 plane | 2–5× | 动态 local fit/cache 难度高；先 CSR，再编译 grow |
| A/B | raster fused bin loop | NumPy 多轮 mask/copy/index + bincount | 1.3–2× raster；端到端收益小 | 原子归约、NaN、边界 bin 一致性 |
| A/B | profile binning/自定义逐点判断 | 若出现 Python loop | 视调用量 | 先 profile；当前主路径证据不足 |
| B NumPy 足够 | mean/min/max/PV/RMS/Rx/Ry、普通 mask | 向量化 NumPy | 单项通常 <30 ms@8M（残差约 0.1 s） | 编译/GPU收益不抵复杂度 |
| B | LOD 的数值准备 | NumPy 向量化但内存重 | 优先算法/缓存/分块，不先 Numba | 全量排序与临时数组才是关键 |
| C SciPy 足够 | cKDTree build/query、ndimage label、lstsq | C/C++/BLAS | `query(workers=6)` 压力测试比 workers=1 快约 4.8–5.4× | 内存带宽、线程过量；逐案启用 |
| D 低收益 | pandas DataFrame 构造、Matplotlib draw、Qt UI | Python/C 扩展对象系统 | Numba不适用 | 应换数据路径/渲染策略 |

SciPy `query` 原生支持 `workers` 参数，[SciPy 文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.KDTree.query.html)。先用它并实测，比重写 KDTree 更合理。

## 10. 多核 CPU

- `ThreadPoolExecutor/QThread`：适合 UI 外执行 NumPy/SciPy/C parser、XY raster、KDTree query；这些底层常释放 GIL。Qt 官方也建议用 worker threads 避免阻塞 GUI，[Qt 文档](https://doc.qt.io/qtforpython-6/overviews/qtdoc-threads.html)。
- Python 逐行 tokenizer、dict/list adjacency、deque grow：普通线程不会形成可靠 CPU 加速，主要价值只在保持 UI 响应。
- `ProcessPoolExecutor`：不适合每次传 5M XYZ。仅 pickle dump/load 2M XYZ 约几十毫秒量级但还未包含 pipe、第二份 RSS、进程启动；实际 topology 已占 GiB，复制会恶化峰值。除非使用 shared memory、长驻 worker 和明确生命周期，否则不建议。
- Numba `parallel/prange`：适合固定数组上的独立 bin/index/edge pass；connected component 和队列 grow 并非简单 prange，应先改 CSR/二维结构，再决定并行策略。[Numba 并行归约文档](https://numba.readthedocs.io/en/stable/user/parallel.html)。
- 同一刷新中不应同时让 OpenBLAS、cKDTree 和应用 executor 全核运行；建议集中管理线程预算，避免 6C 机器过度订阅。

## 11. GPU/CuPy

当前不建议加入 GPU 依赖。RTX 2060 有 6 GiB，但主要 P0 是字符串解析、Python 图结构和 Matplotlib/GUI，而不是大数组算术。

- residual/mask/mean/PV/RMS：CPU 8M 合计仍约百毫秒级；Host→GPU 传 XYZ 已约 183 MiB，还要设备输出和同步。没有稳定复用设备驻留时收益小。
- raster/binning：8M CPU raster 0.464 s，可能有 2–5× kernel 潜力，但全流程还含传输、编译、RGBA 和 GUI upload；优先 CPU fused/chunked 路径。
- morphology/规则 connected component：CPU `ndimage` 已非常快；GPU无优先级。
- Physical topology：GPU 只有在整个 kNN、edge selection、CSR 和 grow 都在设备端时才可能显著受益；当前 6 GiB 很容易被 1M×k 边和临时数组占满，改造风险高。
- CuPy 首次 kernel 编译与缓存必须计入交互体验；官方也明确提示 kernel cache 和不同 reduction 情况，[CuPy 性能文档](https://docs.cupy.dev/en/stable/user_guide/performance.html)。PyInstaller、CUDA runtime/driver、公司电脑无 NVIDIA 或权限限制都会扩大交付矩阵。

可选 GPU backend 仅建议留给 Phase 3 的“超大 raster 聚合”和 Phase 4 的“OpenGL 3D 点云显示”，并保持 CPU baseline 完整可用。

## 13. 优化优先级与预期收益

收益区间基于当前阶段占比和候选 benchmark；“整体”包含现实中不能完全消除的校验、转换和 UI。保守/合理/理想值不是承诺。

### P0

1. 导入 parser dispatch：对识别成功、稳定 schema 的 CSV/TSV/quoted 使用 pandas C `usecols` 数值路径；Z Matrix 用 chunk/fromstring 数值正文，同时保留现有 slow robust fallback、统计和错误语义。预计通用导入 2.5× / 5× / 10×；矩阵 1.5× / 2.5× / 4×。
2. 规则 Matrix Smart ROI 改为隐式网格或紧凑 CSR，删除 Python dict/每点 ndarray；plane-residual 的固定 gate 使用等价二维 component fast path。规则 Smart ROI 总体 2× / 4× / 8×。
3. LOD：避免重复 critical pass、全量副本和 lexsort；按 dataset/display key 缓存，必要时分块选 winner。GUI refresh 1.5× / 2× / 3×；LOD kernel 2× / 4× / 8×。
4. 将全量高阶诊断拟合和 LOD 移出 GUI 线程，并只对真正需要的显示模式计算；保持结果 revision guard。用户感知响应 2× / 3× / 5×，数值计算本身不一定变快。

### P1

1. Physical topology：保留 cKDTree，向量化/Numba 化扇区选边与 local-scale pruning，改紧凑 CSR，利用 `query(workers=线程预算)`。预计 2× / 4× / 6×；仍需限制极大 N 或提供明确 progress/cancel。
2. surface-following grow：CSR + Numba serial kernel，减少 Python deque/标量和局部 plane 分配。预计 2× / 3× / 5×。
3. XY scan-grid：按 dataset 缓存 KDTree/scan pitch，目前 controller 已缓存 grid，但重新 bind/reset 会丢失；预计 cold XY 1.5× / 2× / 3×，cache hit 已约 25 ms。
4. 减少 `update_analysis/draw_plots/Smart worker` 的全量 XYZ/index copy。目标 5M GUI 峰值降低 25% / 40% / 55%，刷新 1.1× / 1.25× / 1.5×。

### P2

- Raster fused CPU kernel：预计 raster 1.3× / 1.7× / 2.2×，但对完整刷新贡献有限。
- Zygo 专用 chunk parser、Pixel 数值 parser：预计 2× / 4× / 7×；必须有真实设备 Golden Files。
- 局部中位数滤波使用 cKDTree `workers`：2M 当前约 5.03 s；预计 1.5× / 2.5× / 4×。
- 多层 Gap query 使用受控 workers：2M 单基准当前约 2.35 s；预计 1.5× / 2.5× / 4×。

### P3

- GPU residual/metrics；平面 `lstsq` Numba 化；仅为全量文本开启 mmap；直接替换全部 Matplotlib；ProcessPool 复制大数组。当前证据不足或风险/收益不佳。

## 14. V4.6.9 Performance 建议架构

### Phase 1：低风险 CPU baseline

- `PERF_DEBUG` 结构化 stage recorder，写日志/CSV，不显示在正式 UI。
- parser fast-path + robust fallback；数值 buffer/`usecols`；matrix 单次扫描状态机。
- dataset revision keyed caches：transform、scan grid、LOD、high-order diagnostics。
- 分离 authoritative metrics 与 optional display diagnostics；后台任务加 run-id，旧结果不得覆盖新输入。
- 所有 fast path 先通过 Golden Files/Golden Masks，再成为默认。

### Phase 2：Numba/紧凑拓扑/线程预算

- matrix implicit-grid/CSR；Physical edge selection+pruning CSR；Numba optional（未安装时 CPU NumPy/SciPy baseline）。
- SciPy query workers 统一受 `PerformancePolicy` 控制；避免与 OpenBLAS/executor 过量并发。
- LOD/raster 分块、复用工作缓冲、减少副本。

### Phase 3：可选 GPU

- 只 benchmark raster aggregation；明确 host/device residency 和 crossover N。
- wheel/installer 不强依赖 CUDA；运行时能力检测、CPU fallback、同一 Golden output。

### Phase 4：高性能 renderer

- XY raster 可评估 PyQtGraph ImageItem；3D 高交互需求评估 VisPy 或 PyVista/VTK。
- Matplotlib 保留报告、打印和静态导出；renderer 只消费 display LOD，不参与量测。

## 16. 正确性门槛

每个优化必须在同一输入、映射、单位、变换、滤波与 ROI 参数下比较：Rx、Ry、法向 PV/RMS、TTV、Mean Z；高阶 residual 属于单独的垂直残差定义。默认要求关键 mask bit-for-bit 一致；浮点指标用基于当前数值范围的明确 `rtol/atol`，不得用抽样结果冒充全量一致。

必须覆盖 quoted CSV、辅助文本列、bad rows、所有 missing token、Zygo `No Data`、矩阵孔洞/行尾终止符、Pixel origin/pitch、matrix8/sample_matrix8/Delaunay/adaptive kNN、cache hit/invalidation、取消与 late-result guard。任何 fast path 无法证明等价时必须回退现有 parser/算法。
